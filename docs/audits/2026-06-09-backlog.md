## A. 大重构（先拉 architect 定方案，再分阶段实施）

### A1. task 生命周期协调器（主题一根治）· 价值高
- **现状**：SC-1~4 + CONC-01 已逐点止血，但根因仍在——`requirement` 与 `task` 两套状态机 + 四个驱动者
  （runner Push / watcher / scheduler / 用户操作）没有单一协调层，终止/级联/并发抢占散落在各 RPC handler。
- **方向**：抽一个统一的「task 生命周期协调器」承接所有 cancel/级联/并发抢占；`requirement-clarifier`
  的 `_inflightRounds` 串行锁是项目内已有的正确范式可推广。
- **defer 原因**：跨内核多模块的结构性重构，需 architect 定边界 + 迁移路径 + 回归面评估。
- **做之前**：architect 输出协调器的职责边界、与现有 bridge/scheduler 的关系、分阶段迁移计划。

### A2. JWT 鉴权一等化（SEC-1 + SEC-6 + WS-JWT）· 价值中高
- **现状**：登录（JWT）仅客户端 AuthGate 生效，服务端 `checkAuth` 在无 API token 时全放行（loopback 豁免
  保护本地 CLI/TUI）。本轮试写 `!hasAnyUser()` 版本后**回退**——会造成 HTTP 强制 JWT 但 WS 不支持 JWT 的
  半不一致。
- **方向**：三处一起改才完整——`checkAuth`（hasAnyUser 时非 loopback 强制）+ WS 升级鉴权加异步 JWT 校验
  + `0.0.0.0` 启动门感知登录（SEC-6），让 JWT 成为 LAN 上的一等鉴权。
- **defer 原因**：动鉴权核心 + WS 异步热路径，半修危险。
- **做之前**：architect 定鉴权模型（token vs JWT 各自边界）；需配 HTTP/WS 两路径鉴权测试。
